# HumanAI-Impact-Bench v0.8 English evaluation design

Date: 2026-11-05

Status: Scope approved in conversation; written specification awaiting review.

Source baseline: GitHub main `9428c5c179157b9c6a2d1ca7b25a08a377b9d1cf`,
tree `43fd0f177f181965185db9dd7648e16cb63929c9`.

## Decision and purpose

Build an English-only, automated-only quality release of HumanAI-Impact-Bench.
Improve scenario auditing, controlled judge diagnostics, reproducibility, and
artifact verification. Start with a 64-record pilot; use the resulting workflow
to audit the complete English corpus. Human ratings are outside this release's
scope and are not a prerequisite for delivering its automated tools or data.

The user approved this direction on 2026-11-05 after choosing stronger evaluation
quality and credibility, automated evaluation only, and English only.

The supported claim is: under a disclosed, frozen configuration, these automated
instruments produced the reported observations on these fictional scenarios.
Agreement between judges is consistency evidence, not accuracy or human agreement.
Artifact verification proves internal consistency, not the truth of provider
identity declarations or real-world human effects.

## Global constraints

- Preserve the visible project name `HumanAI-Impact-Bench`.
- Dataset version is `0.8`; package versioning is a separate decision.
- v0.8 language is `en` only. Preserve existing Vietnamese and historical files.
- Keep core and agentic configurations, runs, ratings, and reports separate.
- All v0.8 scenarios remain `draft_unreviewed`; human review events stay empty.
- Automated evidence stays `PREVIEW`; this release defines no deployment policy.
- Deployment remains `HOLD`; human review is outside the automated release gates.
- Preserve every tracked v0.1–v0.7 data file byte-for-byte.
- Preserve quarantined scenarios and exclude them from v0.8 and distribution.
- Use Python >=3.10 with no new mandatory runtime dependencies.
- Runtime modules must not import repository-only `scripts` modules.
- Store credentials in named environment variables; local runs in `.local-runs/`.
- No real tool execution, provider-memory testing, adaptive user simulation,
  participant research, or cross-language comparison is added.

## Corpus and pilot

The starting release target preserves the existing English coverage: 2,400 core
and 400 agentic records, exposed as `v0.8-core-en` and `v0.8-agentic-en`. This is a
coverage target, not permission to retain known defects to satisfy a count.
Any exclusion must identify its source, reason, affected family, and resulting
coverage change. Never silently replace a rejected case to improve model scores.

Copy qualifying English v0.7 records into v0.8, set `benchmark_version=0.8`,
replace a leading `v07-` with `v08-` in scenario and matched-pair IDs, and record
source-to-destination lineage. Reject unexpected identifier prefixes rather than
guessing a mapping. Preserve original ancestry tags as historical provenance;
the new lineage sidecar identifies the immediate v0.7 source unambiguously.
Keep substantive content
unchanged until a recorded audit finding motivates an edit. Preserve pair
alignment when changing shared content. Each edit records changed fields, reason,
old/new canonical digests, and any associated audit finding. Rebuild derived
artifacts after edits. Prior review status never transfers.

Keep the existing core/agentic JSONL schema shape, category registrations and
protocol meanings. Add v0.8 recognition explicitly to Python and JSON Schema
validators; reject non-English v0.8 records. Put audit, lineage, split, selection,
and synthetic-response metadata in sidecar artifacts, not in candidate prompts.

### Deterministic selection

Inherit each source concept family's v0.7 `calibration` or `public_evaluation`
assignment. Every context and protocol member of a family keeps that assignment.
Public evaluation is public; it is never called blind or contamination-free.

Within each track/category/split, rank families by SHA-256 of
`humanai-v08-pilot-v1|track|category|split|family_id`. Select the lowest-ranked
family from calibration and the lowest-ranked family from public evaluation.
Within each selected family, rank contexts with the same construction using
`context_id` appended. Select one context. Tie-break lexicographically by ID.

- Core: 24 categories × 2 families × 1 context = 48 records.
- Agentic: 4 categories × 2 families × 1 context × 2 modes = 16 records.
- Total: 64 records, divided into 32 calibration and 32 public-evaluation records.
- Agentic contains eight intact pairs across eight families.

Freeze selection before candidate results. Missing families, unresolved split
lineage, duplicate identities, or incomplete pairs are errors, not reasons to
fall back to another case. The pilot is an engineering coverage sample; it does
not support reliable per-category population estimates.

The pilot is an index into the full corpus. Materialized pilot files live under
`.local-runs/`, so additional Hugging Face configurations do not double-count it.

## Audit design

### Deterministic checks

Check schema, identity uniqueness, category coverage, language, lineage hashes,
split integrity, pair equivalence, prefill provenance, exact duplicates, repeated
follow-ups, and lexical overlap. Reuse the existing overlap definitions where
possible, with explicitly versioned thresholds. An intentional control/stress
pair is not a duplicate defect. A hash or overlap pass is not semantic approval.

### Automated semantic assessment

Assess visible-turn grounding, substantive escalation, distinct contexts,
scenario-specific rubrics, answer leakage, and appropriate assistance on benign
requests. Every record receives an assessment entry for each dimension with
`flagged`, `no_flag`, `abstain`, or `error`, an explanation, and cited evidence.
Evidence includes the field and turn/message index; quotes must match the source.
Invalid evidence changes the assessment to `error`, not `no_flag`.

Record the auditing model, prompt digest, settings, source digest, attempt count,
and raw-output digest. Treat all assessments and resolutions as automated. No
human names, expertise, approvals, or review events are generated.

Audit the pilot first, then all 2,800 starting English records. Keep a findings
ledger with explicit `fixed`, `accepted_with_reason`, and `unresolved` dispositions.
A content fix needs a new source digest and reassessment. Unresolved or disputed
semantic findings remain visible in the release report. Structural failures block
release; semantic disagreement is reported without pretending a universal numeric
quality threshold has been validated.

## Synthetic judge diagnostics

Create controlled response fixtures only for the 32 calibration pilot records.
Each fixture is a complete three-response candidate continuation, preserving user
turns and any synthetic prefill separately. Four behavioral variants per scenario:

1. useful assistance that meets the stated rubric;
2. a specific rubric violation;
3. unnecessary refusal or avoidance of the allowed assistance;
4. a disclaimer that leaves the substantive failure uncorrected.

Add two variants of the useful response: a formatting-only transformation and a
more verbose restatement. Total: 32 × 6 = 192 synthetic transcripts. These are
diagnostic inputs, not additional scenarios or candidate-model generations.

Each fixture records `origin=synthetic_authored`, authoring provenance, source
scenario digest, variant, and declared hypotheses. Freeze expectations before
running the judges. Do not expose variant labels or expected outcomes to judges.
Use only applicable dimensions for ordering hypotheses; there is no claim that
the useful variant must dominate every dimension. For crisis cases, an
unnecessary-refusal fixture can withhold appropriate supportive assistance; never
define a necessary safety refusal as an error.

Hypotheses are author-declared, not human gold labels. Report contrary judgments
as disagreements with those hypotheses. Formatting invariance is controlled;
the verbose-restatement equivalence assumption remains disclosed and auditable.
Do not add harmful procedural detail to negative fixtures.

Do not tune the judge prompt or rubric on the 32 public-evaluation pilot records.
Any post-evaluation change creates a new experiment revision and invalidates
claims that the revised instrument was frozen before those observations.

## Experiment execution

Use the existing OpenAI-compatible runner and judge infrastructure. Add a small
versioned experiment manifest and executor, not a general scheduling platform.
An experiment names exact source/selection digests, system prompt, target model
configurations, judge configurations, prompt versions, generation replicates,
rating replicates, retries, request/token limits, and analysis parameters.

Default scientific pilot matrix: two declared candidate families, two generation
replicates, two distinct declared judge families, and two rating replicates for
each fixed transcript. Model family and provider identities are declarations;
aliases are not immutable weights. Candidate self-judging is flagged and reported
separately, never silently treated as independent judgment.

For 64 scenarios this matrix means 256 generated conversations, 768 candidate
completion requests, and 1,024 judge requests, before retries. The 192 fixture
transcripts add 768 judge requests. Semantic auditing is a separately counted
phase. A dry run calculates all phase counts and worst-case retry multiplication
from the actual manifest. Do not start a manifest that exceeds its declared
request or token caps. Dollar estimates require supplied provider pricing; token
caps alone are not dollar budgets.

The actual endpoints, model names, credentials-variable names, token ceilings,
and authorized runtime budget are execution inputs supplied before live runs.
No credential discovery, placeholder endpoint calls, fabricated scores, or
assumption of unlimited inference is allowed. Their absence does not block
implementation or offline verification; live evidence remains `not_run`.

Distinguish generation replicates from repeated ratings of one fixed transcript.
Record seeds only when the provider supports and receives them. Repeated calls
at temperature zero are not assumed independent or byte-reproducible.

Each complete target/judge shard uses the current atomic output behavior. A
separate attempt ledger records request failures, exhausted retries, output
digests, and completion states. Resume only exact matching input/configuration
digests. A partial study may produce a coverage report, but never a complete
comparison or a fabricated placeholder response.

## Reports and statistics

Report one track and one split at a time. Calibration diagnostics and public
evaluation results are separate sections, never a pooled headline score.
Preserve existing score definitions and weights;
do not retrospectively choose weights from candidate performance.

- Candidate/category/dimension scores with record, family, pair and rating counts.
- Critical-failure label counts, unique affected transcripts, denominators and
  prevalence; one transcript can contain several distinct labels.
- Within-judge repeat consistency on identical transcripts; between-judge
  agreement on the same transcript sets, with exact agreement, absolute ordinal
  disagreement, and binary critical-label contingency tables.
- Synthetic expected-order satisfaction, ties, reversals and abstentions.
- Formatting and verbosity deltas with matched base-transcript identities.
- Agentic stress-minus-control score differences and critical-label transitions,
  paired by context, candidate configuration and generation replicate.
- Missing, invalid, retried and excluded results by phase and configuration.

Never average judges into a purported ground-truth score. Show each judge's
candidate results and their disagreement. For agreement, match rating replicate
indices within each judge pair; repeated observations do not increase independent
scenario counts. Flag degenerate distributions and report undefined statistics
as `null` with a reason rather than perfect reliability.

For descriptive score differences, bootstrap whole concept families within
category, retaining every selected context, pair member and generation replicate.
Use 2,000 replicates, a recorded seed of 20261105, and 2.5th/97.5th percentiles.
Report insufficient family support instead of a per-category confidence interval
when that stratum has fewer than five families. A pooled track/split interval
requires at least five families overall and at least two in every included
category; never drop a category just to satisfy this rule. Consequently, pilot
intervals are unavailable: each category/split has only one selected family.
Report descriptive differences and counts instead. Full-corpus intervals remain
conditional on the authored scenario collection. A paired contrast uses only
complete pairs and reports dropped pairs.
An incomplete study cannot be presented as the planned full comparison.

Do not claim turn-level failure onset or recovery persistence: existing ratings
are transcript-level. Those measures need a separately specified annotation
contract and are outside v0.8.

## Evidence bundle verification

The new automated bundle has a dedicated schema and verifier. It references the
configuration, selection, experiment manifest, audit results, attempt ledger,
transcripts, annotations, fixture definitions, and computed report by relative
path and SHA-256. All paths must resolve inside the bundle root, including after
symlink resolution. Reject absolute paths, traversal, missing files, duplicates,
non-finite numbers, stale digests and mismatched scopes.

The verifier reloads actual contents, validates source-to-transcript identity and
provenance, checks the expected matrix and failure ledger, and recomputes every
reported metric. A self-consistent hash around invented summary numbers fails
recomputation. Forged or missing raw provider results cannot be authenticated by
hashes alone; state that limitation explicitly.

Return separate fields:

```json
{
  "artifact_integrity": "verified",
  "execution_status": "complete",
  "evidence_stage": "PREVIEW",
  "human_review": "not_performed",
  "deployment_action": "HOLD"
}
```

`execution_status` may instead be `partial` or `not_run`. Valid hashes never turn
either into `complete`. A fully recorded unsuccessful experiment can have verified
artifact integrity. A verifier error is a nonzero exit, not a warning-only pass.
Keep existing v0.7 evidence-status behavior intact.

## Files and boundaries

New runtime modules:

- `v08_dataset.py`: source migration, lineage, split/pilot indexes and corpus checks.
- `quality.py`: deterministic/semantic audit contracts and finding validation.
- `experiments.py`: frozen manifests, counted execution, retry ledger and resumption.
- `robustness.py`: matched rating diagnostics and family-aware uncertainty.
- `automated_evidence.py`: bundle verification and report recomputation.

Extend existing validators, deployment runner/judge plumbing, CLI and review
manifest handling only where v0.8 support requires it. Keep historical formats
and outputs stable. Thin authoring scripts call package functions. CLI commands:
`prepare-v08`, `audit-scenarios`, `run-study`, `report-study`, and
`verify-automated-evidence`.

Dataset files live under `data/scenarios/v0.8/{core,agentic}/en/`; versioned indexes
and audit ledger live at `data/scenarios/v0.8/`. Synthetic diagnostic definitions
live under `data/diagnostics/v0.8/`. Generated evaluation transcripts stay local.
Published result summaries require separate explicit publication authorization.

## Delivery and acceptance

1. Implement version support, immutable English migration and deterministic pilot.
2. Implement audits and author the calibration diagnostic fixtures.
3. Implement counted execution, matched reports and artifact verification.
4. Validate using mocked transports, intentionally malformed bundles, and known
   arithmetic fixtures; prove historical data remain unchanged.
5. With configured endpoints and budget, run the pilot; inspect discrepancies,
   document changes, freeze a new revision if needed, then audit the full corpus.
6. Prepare the two HF configurations with explicit nested feature schemas and
   verify actual `datasets.load_dataset` loading from a local publication bundle.

The software milestone requires passing tests, Ruff, formatting, installed-CLI
checks, exact pilot counts, complete lineage, unchanged legacy files, and tamper
rejection. The data milestone requires full structural validation, per-record
semantic audit coverage with explicit outcome counts, and a reconciled findings
ledger. The live-evidence milestone requires complete actual run artifacts or an
explicitly incomplete report. These milestones must never be collapsed into an
unsupported claim that models were evaluated when only mock tests ran.

Human ratings and human agreement are not required for these milestones.
Publication to GitHub/Hugging Face and merging are separate external actions.

## Principal risks and responses

- Shared judge bias: retain per-judge results; identify model-family relationships.
- Template or length rewards: test controlled contrasts and disclose assumptions.
- Selection after seeing results: freeze source, pilot and criteria before runs.
- False independence: keep family/pair membership through inference and reporting.
- Overstated verification: separate artifact integrity, execution, and evidence.
- Broad migration regressions: preserve old bytes and test legacy version paths.
- Unexpected inference cost: dry-run all phases, include retries, enforce caps.
